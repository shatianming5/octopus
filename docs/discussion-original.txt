我会把它先设计成一个 Octopus Runtime v0.1。底层尽量借 vLLM 现有的 paged KV / prefix caching，而不是自己先写 attention kernel。vLLM 现在的 KV cache 本身已经是 block 化管理，并且 KVCacheManager 有 request→block 映射、block ref count、prefix reuse、allocate/free 等机制，这和我们需要的“共享 trunk + 私有 branch”非常接近。

1. 最核心的数据结构

我希望整个系统最终只有四种一级对象：

OctopusSession
      │
      ├── Checkpoint
      │       │
      │       ├── Branch A
      │       ├── Branch B
      │       └── Branch C
      │
      └── WorldState

对应 Python：

@dataclass
class OctopusSession:
    session_id: str
    brain_branch_id: str
    current_checkpoint_id: str
    world_state: "WorldState"
    active_branches: dict[str, "Branch"]

Checkpoint 不保存一份真实 KV copy，而保存 KV block references：

@dataclass
class Checkpoint:
    checkpoint_id: str

    # logical inference state
    token_ids: list[int]
    num_tokens: int

    # physical KV state
    block_ids: list[int]

    # position / model consistency
    next_position: int
    model_id: str

    # lifecycle
    ref_count: int
    sealed: bool

关键是：

Checkpoint ≠ KV copy

Checkpoint = immutable KV view
2. 为什么 checkpoint 必须 immutable

假设 Brain 已经运行到：

A B C D E F

其 KV：

[P0][P1][P2]

创建：

Checkpoint C0

之后 C0 永远不改变。

然后：

                   C0
            [P0][P1][P2]
              /    |    \
             /     |     \
            A      B      C

三个 branch 都只引用：

P0 P1 P2

ref count：

P0.ref = 4
P1.ref = 4
P2.ref = 4

包含 Brain 本身。

Branch A 后面生成：

x y z

就变成：

Branch A

[P0][P1][P2][A0]

Branch B：

[P0][P1][P2][B0][B1]

完全没有复制原来的 KV。

这实际上就是：

Copy-on-Write inference state

vLLM 目前的 PagedAttention/KV block 设计本来就允许逻辑 token 序列映射到非连续的物理 KV blocks，并依靠 block pool 管理这些页，所以我们不需要重新发明 KV 内存布局。

最关键的是：

伪代码：

def fork(checkpoint_id, n):

    cp = checkpoints[checkpoint_id]

    branches = []

    for _ in range(n):

        branch = Branch(
            branch_id=new_id(),
            parent_checkpoint_id=checkpoint_id,

            shared_blocks=cp.block_ids.copy(),
            private_blocks=[],

            generated_tokens=[],
            status=RUNNABLE,
        )

        for block_id in cp.block_ids:
            blocks[block_id].ref_count += 1

        branches.append(branch)

    return branches

注意：

cp.block_ids.copy()

只是复制：

[17, 31, 42, 99]

这些整数引用。

没有复制 GPU KV tensor。

5. KV block 自身

底层最好类似：

@dataclass
class KVBlock:
    block_id: int

    gpu_slot: int

    ref_count: int

    num_filled_tokens: int

    immutable: bool

    content_hash: bytes | None

    last_access_time: float

这里我想做一个重要约束：

Shared block 必须 immutable。

只要：

ref_count > 1

就不能修改。

如果 branch 正好在一个没有填满的 block 上 fork，这就出现一个问题。

例如 block size = 16：

[P0][P1........]
        ↑
      只有 9 token

如果直接让三个 branch 共享这个 partial block：

A 想往第10格写
B 也想往第10格写

就冲突了。

因此 v0.1 我建议：

Checkpoint 只允许建立在 block boundary。

例如：

16
32
48
64
...

这是一个非常务实的工程简化。

vLLM 当前 prefix caching 也主要围绕完整 block 工作；相同 prefix 即使部分 token 一致，也通常只有完整匹配 block 能直接命中。

6. 后面再支持 partial-block fork

v0.2 可以实现：

[P0][Partial P1]
         │
         fork
         ↓

A:
[P0][copy(P1) → A1]

B:
[P0][copy(P1) → B1]

也就是：

full blocks → zero copy
last partial block → copy

于是额外成本最多：

$$ 1\ KV\ block \times N_{branches} $$

完全可以接受。

8. 一个很重要的新概念：Branch value

以后我会考虑给每个 branch 一个：

$$ V(b) $$

代表继续计算这个 branch 的预期收益。

例如：

$$ V(b)= P(\text{useful result}) \times Impact - ComputeCost $$

这样 Brain 开了：

10 条触手

不代表 10 条都必须跑完。

运行几秒后：

Branch 1: 很有希望
Branch 2: 找错方向
Branch 3: 已经被 Branch 1 覆盖

可以：

kill Branch 2
kill Branch 3

立即释放 private KV。

这才真正像章鱼，而不是传统：

spawn 10 agents
↓
等10个都回来
9. Commit 绝对不能等于 KV merge

这里我们把语义定死。

假设：

          C0
        /    \
       A      B

A KV:
C0 + 4000 tokens

B KV:
C0 + 7000 tokens

执行结束：

A.commit()
B.commit()

我们不会：

merge_kv(A, B)

而是：

commit_a = semantic_commit(A)
commit_b = semantic_commit(B)

然后得到可能：

    "src/auth/cookie.py:42"

Brain 只 consume 这个。

13. abort

abort() 必须非常便宜。

例如：

Branch A:
shared:
P0 P1 P2 P3

private:
A4 A5 A6

abort：

for b in branch.shared_blocks:
    blocks[b].ref_count -= 1

for b in branch.private_blocks:
    free(b)

然后 branch metadata 删除。

复杂度：

$$ O(\#blocks) $$

以后如果 block ref 做得好，可以非常轻。

14. GC

我建议 KV block 分三种：

HOT
ACTIVE shared/request正在使用

WARM
没有 active branch 使用
但属于 checkpoint / prefix cache

FREE
可以立即复用

生命周期：

ACTIVE
  │
  ▼
WARM
  │
memory pressure
  ▼
FREE

Checkpoint：

ref_count = 0

不一定马上清 KV。

可以保留：

LRU

这样用户突然：

回到旧计划

可能直接复用。

这也和 vLLM 当前的 prefix-cache free/eviction 思路比较一致：block 可以不再被 active request 使用但仍留在 prefix cache，之后在内存压力下被 LRU 式复用/驱逐。

我现在认为最关键的设计决定

我们之前说“KV fork”，但现在可以更精确地定义：

$$ \boxed{ \text{Octopus Branch} = \text{Immutable Shared KV Prefix} + \text{Mutable Private KV Suffix} } $$

而：

$$ \boxed{ \text{Commit} \neq \text{KV Merge} } $$

而是：

$$ \boxed{ \text{Commit} = \text{Private Neural State} \rightarrow \text{Semantic Delta} } $$

然后：

$$ \boxed{ C_{t+1} = C_t+\operatorname{Reduce} ( \Delta_1,\Delta_2,\ldots,\Delta_n ) } $$

我觉得到这里，Octopus 已经从“一个想法”变成了一个比较明确的计算模型。

1. Brain 什么时候 checkpoint？

我的第一版答案是：不要每个 token checkpoint，也不要固定只按时间 checkpoint，而采用“语义边界 + 周期 checkpoint”混合策略。

三个天然 checkpoint：

User turn end
↓
Brain completes reasoning/planning
↓
Task graph stabilized
↓
CHECKPOINT

比如：

用户：
帮我修这个 repo 的登录问题

Brain:
1. 看代码
2. 查日志
3. 查文档

          ← checkpoint here

        /       |       \
     Code     Logs      Docs

也就是说，fork 点最好位于“决策已经完成，但外部探索尚未开始”的位置。

这是很合理的，因为所有 branch 都真正共享：

Problem understanding
Global constraints
Current belief
Plan

而不需要共享后续执行。

有趣的是，vLLM 最近针对 agentic workload 的 cache retention 设计也明确认为 prompt boundary 是高价值 checkpoint；同时还允许固定 interval checkpoint，在状态过长时避免只能从头重算。

所以第一版：

$$ Checkpoint = SemanticBoundary \cup PeriodicBoundary $$

例如：

semantic checkpoint:
task decomposition complete

periodic checkpoint:
every 8k / 16k / 32k tokens

然后做 ablation：

A. checkpoint every N tokens
B. checkpoint at turn boundary
C. checkpoint at planning boundary
D. semantic + periodic

我预测 D 最好。

2. 什么时候 fork？

这里不要定义成：

“只要可以并行就 fork。”

太粗糙。

我建议 Brain 计算一个 Fork Utility：

$$ U_{fork} = P_{parallel} \times V_{information} - C_{compute} - C_{merge} - C_{contention} $$

简单解释就是：

这个任务能不能独立做？
↓
不同 branch 会不会获得互补信息？
↓
并行节省的时间值不值得多开的 KV / decode？
↓
回来以后结果是否容易合并？

例如：

查代码
查日志
查官方文档

非常适合 fork。

但：

修改代码
↓
运行修改后的 tests

不适合 fork，因为有强 dependency。

所以实际上 fork 是在 Task DAG 中识别：

$$ \text{independent frontier} $$

例如：

                diagnose
              /    |     \
         code     logs    docs
           \       |      /
              hypothesis
                  |
                 patch
                  |
                 test

同一层 frontier：

code / logs / docs

fork。

然后更难的问题：一个 branch 应该继承多少 KV？

这里我不认为答案是：

所有 branch 永远继承完整 Brain KV。

因为虽然 zero-copy，attention 还是要访问这些 KV。

比如 Brain context：

80k tokens

CodeArm 实际只需要其中：

15k relevant

即使前 80k 的 prefill 不重算，decode 时 attention 仍可能面对巨大 KV context。

所以：

$$ \text{KV sharing} \neq \text{free context} $$

这非常重要。

我会设计三种继承模式
Full Fork
Brain KV:
████████████████████████

Code:
████████████████████████ + local

优点：

完全不丢 context
无需重新 prefill

缺点：

KV memory retained
attention context 大
可能产生无关上下文干扰

它应该成为我们的一个 baseline。

Prefix Fork

只继承到某一个 checkpoint：

Brain:

A────B────C────D────E
               ↑

Arm:
A────B────C────D

比如 Brain 在 E 又进行了一大段与某个 arm 无关的思考，那么触手从 D fork。

这个非常容易实现。

而且我认为实际价值很高。

Selective Context Fork

这是最有研究价值的。

理想情况：

Brain Memory:

[A][B][C][D][E][F][G][H]

CodeArm needs:

[A][C][F][H]

但是这里马上遇到 Transformer 的问题：

KV 不能任意摘块以后拼起来。

因为：

KV(F)

是在：

ABCDE

历史条件下产生的。

所以不能简单：

A + C + F + H

然后当成合法 sequence KV。

因此 v1 不能真正做 arbitrary KV pruning。

我建议用“Shared Trunk + Context Capsule”

这是目前我认为最现实的解决方案。

Branch 保留一段共同 trunk：

Shared Brain KV
██████████████

然后 Brain 给这个触手生成非常短的：

Context Capsule

例如：

{
  "task": "inspect authentication code",
  "relevant_facts": [
    "refresh fails only in Safari",
    "backend token generation succeeds"
  ],
  "relevant_files": [
    "auth/cookie.py"

}

于是：

Shared checkpoint
      +
small task capsule
      +
Arm-local trajectory

我们可以调一个参数：

$$ r = \frac{\text{shared inherited tokens}} {\text{brain tokens}} $$

比如：

100%
75%
50%
25%
0%

然后 benchmark。

这其实会直接回答你：

一个 branch 到底应该继承多少？

答案不应该凭感觉写死，而应该通过：

$$ Quality(r), Latency(r), Memory(r) $$

得到一个 Pareto frontier。

这个最好我们自己做。

我甚至觉得它可能成为论文里面非常漂亮的一部分。

理论上：

传统：

$$ C_{MA} \approx N L_s + \sum L_i $$

Octopus：

$$ C_{Oct} \approx L_s + \sum L_i $$

因此 shared-context saving：

$$ Saving \approx (N-1)L_s $$

这张图应该会非常好看。

最重要的优势指标

不要把论文主 claim 写成：

“Octopus achieves higher accuracy.”

这不一定成立。

我认为最强的 claim 是：

At equal task quality, Octopus substantially reduces redundant context processing and coordination overhead.

然后定义一个指标：

$$ Efficiency = \frac{TaskSuccess} {GPUSeconds} $$

甚至：

$$ Agentic\ Efficiency = \frac{SuccessRate} {\text{Prefill FLOPs}+\lambda\cdot\text{Decode FLOPs}} $$

以及一个我们自己的：

$$ Context\ Redundancy\ Ratio = \frac{ \text{repeated context tokens processed across branches} }{ \text{total context tokens processed} } $$

传统 multi-agent 很可能：

70–90%

Octopus 理想情况下：

10–30%

这会非常直观。

我觉得这个 work 是有潜力的，而且现在已经不只是“多智能体换个名字”了。但它能不能成为一个强 work，关键取决于我们最后把 novelty 压在哪一层。

最有价值的不是“章鱼”这个 metaphor，而是我们实际上提出了一个不同的 agent execution abstraction：

$$ \text{Multi-Agent} = \text{multiple independent contexts} + \text{message passing} $$

变成：

$$ \boxed{ \text{Octopus} = \text{one cognitive state} + \text{forkable inference branches} + \text{semantic commits} } $$

这个区别是实质性的。

我最看好三个点

第一是 KV cache 从优化机制变成 agent runtime primitive。

现在 KV cache 通常被看作 inference optimization：

prefix caching
paged KV
cache eviction

我们的思路是：

KV checkpoint
KV fork
branch
abort
commit
GC

也就是把：

cache

提升成：

cognitive process state

这其实是很漂亮的 conceptual shift。

第二是你一开始提出的那个问题非常真实：

为什么多个 Agent 明明知道大量相同的信息，却还要不停复制、总结、发送 context？

现有 multi-agent 很多时候：

Agent A
   ↓ message
Agent B
   ↓ summary
Agent C
   ↓ result
Orchestrator

而我们试图变成：

              Shared cognitive trunk
                    /   |   \
                   /    |    \
                  A     B     C
                   \    |    /
                    semantic
                     deltas

如果 benchmark 能证明随着 branch 数增加：

$$ C_{\text{multi-agent}}\sim O(NL) $$

而 Octopus 对共享部分接近：

$$ C_{\text{octopus}}\sim O(L+\sum_i\Delta_i) $$

这会是一个非常容易理解的结果。

第三，我其实最喜欢的是：

fork cheap, merge semantic

因为我们没有硬搞：

$$ KV_A+KV_B $$

这种目前很麻烦的东西。

而是承认 Transformer inference state 本身具有路径依赖，然后设计：

$$ \text{Neural fork} \rightarrow \text{independent exploration} \rightarrow \text{semantic commit} $$

这在工程上现实很多。

但这个 work 目前有一个最大的危险。

Reviewer 很可能看完摘要以后说：

“Isn't this just vLLM prefix caching + an agent orchestrator?”

这个问题必须正面解决。

所以如果最后只是：

vLLM prefix caching
+
parallel requests
+
JSON result

我会觉得 work 从 8.5 分掉到 5 分左右。

因为这更多是不错的 systems engineering。

真正把它拉开的东西应该至少有一个非常明确的新 abstraction：

$$ \boxed{ \text{Explicit forkable inference state} } $$

也就是：

cp = brain.checkpoint()

a, b, c = cp.fork(3)

...

brain.commit(a.result)

而不是：

llm.generate(same_prefix + promptA)
llm.generate(same_prefix + promptB)

这两个表面性能可能接近，但 abstraction 不一样。

然后我觉得我们现在发现了一个比原始 idea 更有研究价值的问题：

Context inheritance

我们最开始想：

所有触手共享 Brain KV。

现在发现其实不一定。

因为：

$$ \text{zero-copy KV}\neq\text{zero-cost attention} $$

所以真正的问题变成：

$$ \boxed{ \text{What is the minimum cognitive state required to spawn a capable branch?} } $$

这个问题我觉得非常漂亮。

比如最后实验发现：

100% Brain KV
accuracy 64%
latency 1.00×

50% KV + capsule
accuracy 64%
latency 0.73×

25% KV + capsule
accuracy 62%
latency 0.58%

0% KV + summary
accuracy 54%
latency 0.51%

那么你会得到一个非常有意思的 Pareto frontier。

这时候 work 已经不只是：

“我们做了一个更快的 multi-agent。”

而是在研究：

一个 Agent 分裂出新的执行分支时，到底需要继承多少认知状态？

这个问题明显更深。

甚至可以进一步把 Octopus 看成一种 LLM operating system abstraction：

Memory pages               KV blocks

Scheduler                   Branch scheduler

这个类比不是为了包装，而是真的可以指导设计。

fork()

传统：

spawn agent

意味着：

创建一个新的智能体。

Octopus：

fork cognition

意味着：

这是两种不同的哲学。
