# Recovery trace malformed-command audit

**Bounded conclusion:** The 40 malformed proposals are not length caps, broken XML, fenced calls, missing tool advertisement, or executed tests. All 40 generations ended normally with `finish_reason="stop"` and contained a syntactically complete, unfenced `<function=execute_bash><parameter=command>...</parameter></function>` call. Every proposal was rejected before submission with the identical parser result `error_type="invalid_function_call"` and `error="unsupported command; use the listed read-only adapters, yarn jest, or str_replace_editor for changes"`.

**Exact classification:** 38/40 requested recursive `ls -R`, which the bounded command grammar does not advertise: action 11 used `ls -R /testbed/lighthouse-core`, and actions 13-49 used `cd /testbed && ls -R .`. The other 2/40, actions 7-8, used `find /testbed -type f -name "react.js" -not -path "/testbed/stack-packs/packs/react.js"`; the advertised `find` grammar permits `-type f` plus `-name` or `-iname`, but not `-not` or `-path`. Counts are therefore: unsupported command forms/semantic flags 40, XML syntax errors 0, fence errors 0, missing function/parameter tags 0.

**Advertisement and feedback:** Context 0 explicitly advertises `execute_bash`, a leading `cd PATH && COMMAND`, nonrecursive `ls [PATH]`, restricted `find [PATH] [-type f] (-name|-iname) GLOB`, and `yarn jest [ARGS]`. It explicitly says commands are parsed rather than evaluated by a shell and that unsupported operators or forms do not exist. Thus the function and leading `cd` syntax were available, but `ls -R`, `-not`, and `-path` were not. For every malformed proposal that had a subsequent request, the exact parser feedback is present once in the next compiled capsule: 39/39 contexts, with action 49 terminal at the action cap and therefore having no next input.
